# Потактовая работа предсказателя переходов на коде теста

Захват: `bpred_testcode_20260728.ila` (+ `/tmp/testcode.csv`)
Дата: 2026-07-28. SCR1 @ 30 МГц, Nexys A7-100T.

## 0. Какой предсказатель измеряется — ДИНАМИЧЕСКИЙ, не статический

В собранном битстриме активен **динамический предсказатель направления (BHT)**,
а статический BTFN работает лишь как запасной вариант для необученных записей.
Подтверждения:

- `scr1_arch_description.svh:171` — `` `define SCR1_BP_DYNAMIC `` **включён**;
  `SCR1_BP_BHT_SIZE = 1024`, `SCR1_BP_BHT_IDX_W = 10`.
- `scr1_pipe_ifu.sv:838` — инстанс `scr1_pipe_bht` (2-битные счётчики насыщения с
  битом достоверности, адаптировано из OpenHW CVA6), индексируется
  `ifu_head_pc[10:1]`, обучается из EXU на каждом разрешённом условном переходе.
- `scr1_pipe_bpred.sv:115` — правило выбора:
  ```verilog
  assign cond_taken = bp_bht_valid_i ? bp_bht_taken_i : cond_btfn;
  ```
  то есть **BHT перекрывает BTFN**, как только запись обучена.
- `scr1_pipe_exu.sv:831` — `bp_dir_pred = exu_bp_predicted_taken`, а
  `bp_dbg_pred = bp_dir_pred`. Значит наблюдаемый на ILA сигнал `bp_dbg_pred` —
  это **решение BHT**, а не пересчитанное правило BTFN.
- Лог синтеза: `synthesizing module 'scr1_pipe_bht'`, параметр `SCR1_BHT_SIZE`
  связан со значением 1024. Модуль реально попал в битстрим.

Отсюда: измеренные **2.17% промахов — показатель динамического предсказателя**.
Ранние формулировки в этом и в соседнем отчёте, называвшие предсказатель
«статическим BTFN», ошибочны и исправлены ниже.

## Как увидеть столбец «выборка» в осциллограмме

В таблицах ниже столбец «выборка» — это сигнал `u_ila_0_tcm_imem_addr` в такты,
когда `i_scr1/tcm_imem_req = 1` (при нуле выборки нет, в таблице прочерк). Два
момента, из-за которых его легко не найти:

**1. Нужен файл `_view`.** В `bpred_testcode_20260728.ila` сохранена устаревшая
раскладка от сессии по TCM (`uart_*`, `tcm_dmem_*`) — сигналов выборки там нет.
Сигналы выведены в `bpred_testcode_20260728_view.ila`.

**2. Адрес в осциллограмме ПОСЛОВНЫЙ — и вот почему.** В `nexys4ddr_scr1_debug.xdc`
щуп заказан на все 32 бита (`tcm_imem_addr[0]` … `[31]`), но в захвате их только
**30**: единственная колонка CSV — `u_ila_0_tcm_imem_addr[31:2]`, битов `[1:0]`
нет вовсе. Адрес выборки команд всегда выровнен по слову, поэтому эти два бита в
цепи — константный ноль; синтезатор свернул их в константы и выбросил из щупа
(наблюдать константу нечего), а уцелевший срез Vivado переименовал в `[31:2]`.

Тот же механизм раздробил `bp_dbg_pc` на 13 фрагментов — просто здесь он
проявился аккуратно, одним непрерывным срезом.

Итог: в осциллограмме лежит **сырой захваченный срез** (байтовый адрес без двух
нулевых младших разрядов), а в таблицах отчёта — **восстановленный байтовый
адрес** (значение × 4), потому что с ним сходятся PC переходов и его можно
сверять с дизассемблером.

Корректность восстановления проверена: ни один из 203 восстановленных адресов не
оказался некратным 4, и по адресам переходов **446 обращений из 446** вернули
настоящую команду перехода — при неверном множителе декодирование развалилось бы.

| Такт | В отчёте (байтовый) | В осциллограмме (пословный) |
|---|---|---|
| 2286 | `0xf00015d0` | `0x3C000574` |
| 2287 | `0xf00015d4` | `0x3C000575` |
| 2288 | `0xf00015d8` | `0x3C000576` |
| 2289 | `0xf00015f0` | `0x3C00057C` |
| 2290 | `0xf00015f4` | `0x3C00057D` |
| 2291 | `0xf00015f8` | `0x3C00057E` |

В пословном виде картина даже нагляднее: `574 → 575 → 576` идут подряд — это
последовательная выборка по ошибочному пути, а скачок на `57C` и есть
перенаправление на цель перехода.

Для случая A соответственно: `0x3C0000AF` (продолжение) → `0x3C0000AC`
(ошибочная цель) → снова `0x3C0000AF` → `0x3C0000B0` → `0x3C0000B1`.

## Случай C — попадание (такты 3–25)

Плотный цикл на `0xf00002b8`, период **5 тактов**:

```
такт | brret pred act mis redir | выборка
   3 |   1    1   1   0    0    | 0xf00002b4     <- ретайр, предсказание верно
   4 |   0    1   0   1    0    | 0xf00002b8
   5 |   0    0   0   0    0    |     -
   6 |   0    0   0   0    0    | 0xf00002bc
   7 |   0    0   0   0    0    | 0xf00002b0     <- цель обратного перехода
   8 |   1    1   1   0    0    | 0xf00002b4     <- следующая итерация
```

Главное: **`redirect` не поднимается ни разу**. Конвейер не сбрасывается,
выборка идёт по предсказанной ветви, цикл повторяется каждые 5 тактов ровно.
Это и есть «стоимость» верного предсказания — ноль потерянных тактов.

## Случай A — промах «ждали переход, его не было» (такт 2048)

`PC = 0xf00002b8`, `pred = 1`, `actual = 0` — выход из того же цикла.

```
такт | brret pred act mis redir | выборка
2046 |   0    0   0   0    0    | 0xf00002bc
2047 |   0    0   0   0    0    | 0xf00002b0   <- ОШИБОЧНЫЙ путь: цель перехода
2048 |   1    1   0   1    1    | 0xf00002bc   <- ретайр, промах, redirect
2049 |   0    1   0   1    0    | 0xf00002c0   <- пошли по верному пути
2050 |   0    1   0   1    0    | 0xf00002c4
2051 |   0    0   0   0    0    | 0xf00002c8
```

Механика: предсказатель считал, что цикл продолжится, и на такте 2047 выбрал
команду по адресу цели `0xf00002b0`. Цикл завершился — на такте 2048 при ретайре
обнаружено расхождение, поднят `redirect`, выборка **в тот же такт** развёрнута
на `0xf00002bc` (продолжение после перехода). Потеряна одна выборка (`0xf00002b0`).

## Случай B — промах «ждали продолжение, был переход» (такт 2289)

`PC = 0xf00015d0`, `pred = 0`, `actual = 1`.

```
такт | brret pred act mis redir | выборка
2286 |   0    1   0   0    0    | 0xf00015d0   <- сам переход
2287 |   0    1   0   0    0    | 0xf00015d4   <- ОШИБОЧНЫЙ путь: продолжение
2288 |   0    0   0   0    0    | 0xf00015d8   <- ОШИБОЧНЫЙ путь
2289 |   1    0   1   1    1    | 0xf00015f0   <- ретайр, промах, redirect на цель
2290 |   0    0   0   0    0    | 0xf00015f4
2291 |   0    0   0   0    0    | 0xf00015f8
```

Зеркальная картина: предсказали «перехода не будет», выбирали продолжение
(`15d4`, `15d8`), а переход состоялся. На такте 2289 `redirect` разворачивает
выборку на настоящую цель `0xf00015f0`. Потеряны **две** выборки.

## Цена промаха

`redirect` поднимается **в тот же такт**, что и `mispred` — задержка ноль во всех
10 промахах окна. Потери ограничены уже начатыми выборками по ошибочному пути:

- случай A — 1 такт,
- случай B — 2 такта.

Это следствие короткого конвейера SCR1: расхождение обнаруживается рано, глубоко
уйти по неверному пути конвейер не успевает.

Практический вывод: при доле промахов **2.17%** и штрафе 1–2 такта потери на
неверных предсказаниях составляют порядка **2–4% тактов выборки**. Поскольку BHT
здесь уже работает (см. п. 0), это не оценка «что даст динамика», а **достигнутый
результат динамического предсказателя**. Дальнейший запас невелик: даже идеальный
предсказатель убрал бы лишь эти 2–4%.

Направления, где ещё есть что выигрывать, — не в увеличении таблицы, а в
устранении конкретных источников промахов:
- переходы, встречающиеся однократно (`0xf0000314`, `0xf0000324`, `0xf0001120`,
  `0xf0000840` — по 1 ретайру): запись BHT не обучена, работает запасной BTFN.
  Их не лечит никакой размер таблицы;
- эффект «разогрева» после смены фазы программы (пример — `0xf00015fc`, п. про
  траекторию счётчика): один промах на смену поведения — цена гистерезиса
  2-битного счётчика;
- возможное наложение записей (индекс — всего `PC[10:1]`, 1024 записи без тега):
  в захваченном окне наложений между наблюдаемыми PC нет, но на полной программе
  их стоит проверить отдельно.

### Это не аномалия, а работа BHT (исправление раннего вывода)

Два последних случая противоречат правилу BTFN — и именно поэтому доказывают,
что предсказания формирует **обученный BHT**, а не статическое правило.
Проверка по всем 458 ретайрам:

| PC | Направление | Всего | `pred=1` | `pred=0` |
|---|---|---|---|---|
| `0xf00002b8` | назад | 410 | 410 | 0 |
| `0xf00015fc` | назад | 32 | 31 | **1** |
| `0xf0001120` | назад | 1 | 0 | **1** |
| `0xf00015d0` | вперёд | 2 | **1** | 1 |

То есть **одна и та же команда получает разные предсказания в разные моменты**.
Для статического предсказателя это невозможно, для обучаемого — норма.

Самое наглядное свидетельство — `0xf00015d0`, переход **вперёд** (`beq a0, a5, +32`),
один раз предсказанный как **состоявшийся**. Правило BTFN такого дать не может в
принципе: вперёд всегда «не состоится». Значит направление задал BHT.

Траектория `0xf00015fc` (переход назад, 32 ретайра) читается как поведение
2-битного счётчика насыщения:

| Такт | pred | actual | Что произошло со счётчиком |
|---|---|---|---|
| 2331 | 1 | 0 | промах; счётчик из «слабо taken» (10) уходит в «слабо not-taken» (01) |
| 2865 | 0 | 1 | промах; счётчик возвращается в «слабо taken» (10) |
| 2906 … 4066 | 1 | 1 | 30 ретайров подряд без единого промаха — счётчик насыщается |

Ровно этого и ждут от 2-битного счётчика: одиночное отклонение сдвигает состояние,
но устойчивое поведение быстро восстанавливает верное предсказание.

**Исправление раннего вывода.** В первой редакции этого отчёта расхождение
объяснялось условием из `scr1_pipe_ifu.sv:940`:

```verilog
assign bp_redirect_req   = bp_any_taken & bp_instr_consumed & ~exu2ifu_pc_new_req_i;
```

— предсказание якобы «терялось» при остановке конвейера. Это объяснение
**неверно** в качестве причины наблюдаемого: указанное условие управляет тем,
произойдёт ли перенаправление **выборки**, тогда как `bp_dbg_pred` берётся из
`exu_bp_predicted_taken`, то есть из бита, прочитанного в BHT и пронесённого с
командой. Значение `pred = 0` на переходе назад означает именно решение BHT, а не
потерю предсказания. Совпадение с остановками выборки (такты 2856–2862 перед
событием 2865) — сопутствующее обстоятельство, а не причина.

## Отдельно: почему сигналы нельзя читать вне тактов ретайра

Посмотрите на такт 4 в случае C: `pred = 1`, `actual = 0`, `mispred = 1` — но
`brretire = 0`. Это **не промах**, а удержанное с прошлого такта значение.
Такая картина повторяется каждую итерацию цикла (такты 4, 9, 14, 19, 24).

Если наивно считать промахи потактово, в цикле с **нулём** промахов получится
«один промах на пять тактов = 20%». В отдельном захвате (`bpred_cycles`)
`mispred` держался поднятым 850 тактов подряд при двух реальных промахах —
завышение в 400 раз.

Отсюда правило: **`pred`, `actual` и `mispred` достоверны только при
`brretire = 1`.** Любой подсчёт и любое триггерное условие обязаны включать это
через `AND`. Именно поэтому в захвате статистики применялась квалификация
хранения по `brretire` — она отбирает ровно достоверные такты.

# Данные симуляции: вклад частей и цена промахов

Захват ILA показывает механику на реальном железе, но охватывает окно в 4096
тактов. Числа по программе целиком получены в verilator (`CFG=MAX`, `rv32imc`),
прогоном одной и той же пары тестов на четырёх сборках предсказателя.

## Лесенка конфигураций

| Конфигурация | Dhrystone, тактов | CoreMark, тактов |
|---|---|---|
| предсказатель выключен | 369 | 5014 |
| + BTFN (`SCR1_BPRED_EN`) | 346 | 4917 |
| + RAS (`SCR1_BP_RAS_EN`) | 345 | 4905 |
| + BHT (`SCR1_BP_DYNAMIC`) | **343** | **4789** |

Вклад каждой части:

| Часть | Dhrystone | CoreMark |
|---|---|---|
| BTFN | −23 такта (−6.2%) | −97 тактов (−1.9%) |
| RAS | −1 такт (−0.3%) | −12 тактов (−0.2%) |
| **BHT** | −2 такта (−0.6%) | **−116 тактов (−2.4%)** |
| **итого** | **−26 (−7.0%)** | **−225 (−4.5%)** |

**На CoreMark динамический BHT — крупнейший вклад из трёх, больше статического
BTFN.** На dhrystone он почти не виден. Причина в составе нагрузки: dhrystone
на ~95% состоит из обратных дуг циклов, которые BTFN предсказывает и без
обучения; CoreMark (конечный автомат, обход списка, матричные операции)
ветвится разнообразнее, и обучаемая таблица там начинает работать.

Отсюда методическое требование: **судить о предсказателе по одному dhrystone
нельзя** — вывод получится противоположным.

## Счётчики переходов и промахов

В `scr1_pipe_exu.sv` под `` `ifdef SCR1_TRGT_SIMULATION `` добавлены счётчики
(на синтез и на плату не влияют). Значения — суммарные по обоим тестам, так как
оба прогоняются в одной симуляции.

| Конфигурация | Тактов | Переходов | Взято | Промахов | Доля промахов |
|---|---|---|---|---|---|
| выключен | 622111 | 61952 | 32069 | 32069 | 51.8% |
| BTFN | 603325 | 61952 | 32069 | 11595 | 18.7% |
| BTFN+RAS | 601995 | 61952 | 32069 | 11595 | 18.7% |
| **полный (BHT)** | **589931** | 61952 | 32069 | **4184** | **6.75%** |

Проверки состоятельности: число переходов и число взятых одинаковы во всех
сборках (программа не меняется); в конфигурации «выключен» промахов ровно
столько же, сколько взятых переходов — при отсутствии предсказания любой взятый
переход считается промахом; RAS не меняет счёт условных переходов, поскольку
работает на возвратах (`JALR`).

**BHT сократил промахи с 11595 до 4184 — на 64%.**

## Цена одного промаха

Штраф выводится из переходов между сборками — прямого измерения «идеального»
предсказателя не существует, но разница сборок даёт его численно:

| Переход | Δ тактов | Δ промахов | Тактов на промах |
|---|---|---|---|
| выключен → BTFN | 18786 | 20474 | **0.92** |
| BTFN+RAS → BHT | 12064 | 7411 | **1.63** |

Разница между 0.92 и 1.63 содержательна. Когда предсказателя нет, взятый переход
просто перенаправляет выборку в момент разрешения — работа по неверному пути не
выполнялась. **Неверное же предсказание дополнительно тратит такты на выборку по
ошибочному пути**, что и видно в захвате ILA (случаи A и B: 1–2 отброшенные
выборки). Поэтому промах обходится дороже, чем отсутствие предсказания.

## Сколько теряем сейчас и каков потолок

```
остаточные потери ≈ 4184 промаха × 1.63 такта ≈ 6800 тактов ≈ 1.2% времени
```

Это верхняя граница выигрыша от **идеального** предсказателя. Для сравнения, уже
отыграно 32180 тактов = **5.2%**, из них на долю BHT приходится 12064.

# Разбор предсказаний по захвату ILA

Ниже — почему предсказатель принял именно такие решения на каждом переходе из
захвата `bpred_testcode_20260728.ila`. Индекс BHT считается как `PC[10:1]`
(1024 записи, тегов нет).

| PC | Индекс BHT | Ретайров | Взято | `pred=1` | Промахов |
|---|---|---|---|---|---|
| `0xf00002b8` | 348 | 410 | 409 | 410 | 1 |
| `0xf00015fc` | 766 | 32 | 31 | 31 | 2 |
| `0xf00015e0` | 752 | 7 | 6 | 7 | 1 |
| `0xf0001110` | 136 | 3 | 1 | 0 | 1 |
| `0xf000110c` | 134 | 2 | 0 | 0 | 0 |
| `0xf00015d0` | 744 | 2 | 2 | 1 | 1 |
| `0xf0000314` | 394 | 1 | 0 | 1 | 1 |
| `0xf0000324` | 402 | 1 | 0 | 1 | 1 |
| `0xf0001120` | 144 | 1 | 1 | 0 | 1 |
| `0xf0000840` | 32 | 1 | 1 | 0 | 1 |

**Наложений индексов среди наблюдавшихся переходов нет** — каждый занимает
собственную запись. Значит поведение каждого объясняется его личной историей, а
не влиянием соседей: это устраняет главную неоднозначность при разборе.

## Обученная запись, устойчивое поведение

`0xf00002b8` (`bne a1, a2, −8`) — 410 ретайров, из них 409 взято, и **все 410 раз
предсказано «состоится»**. Счётчик насыщен в состоянии «уверенно taken» и не
шелохнулся от единственного невзятого исполнения — в этом и смысл двухбитного
счётчика: одиночное отклонение не сбивает предсказание. Единственный промах —
выход из цикла, устранить его нельзя ничем, кроме предсказания длины цикла.

`0xf000110c` — 2 ретайра, оба не взяты, оба предсказаны верно, промахов нет.
Запись обучена в «не состоится».

## Обучение в действии

`0xf00015d0` (`beq a0, a5, +32`, переход **вперёд**) — 2 ретайра, оба взяты.
Первый предсказан как «не состоится» (промах), второй — уже как «состоится»
(верно). Это **прямое доказательство обучения**: статическое правило BTFN для
перехода вперёд обязано всегда давать «не состоится», и второе предсказание
было бы снова ошибочным. Именно этот случай отмечен маркером 3 в захвате.

`0xf00015fc` — самая показательная траектория, 32 ретайра и 2 промаха:

| Такт | pred | actual | Состояние счётчика |
|---|---|---|---|
| 2331 | 1 | 0 | из «слабо taken» уходит в «слабо not-taken» |
| 2865 | 0 | 1 | возвращается в «слабо taken» |
| 2906 … 4066 | 1 | 1 | 30 верных подряд, счётчик насыщается |

Смена фазы программы стоила двух промахов, после чего предсказание
восстановилось. Это цена гистерезиса — и одновременно его польза: без него
колебания были бы постоянными.

## Необученные записи: работает запасной BTFN

`0xf0000314` и `0xf0000324` (`bne`, смещения −16 и −8) — по одному ретайру,
оба **не взяты**, но предсказаны как «состоится». Запись BHT пуста, поэтому
сработало статическое правило: переход назад → «состоится». Правило ошиблось.

`0xf0000840` (`bge a5, s1, +16`, вперёд) — один ретайр, взят, предсказан как
«не состоится». Снова необученная запись и правило BTFN, снова ошибка.

Эти три промаха **не лечатся увеличением таблицы**: переход встречается первый
раз, обучаться не на чем. Это неустранимый минимум для любого обучаемого
предсказателя.

`0xf0001120` (`bne a0, s4, −16`, назад) — один ретайр в окне, взят, но предсказан
как «не состоится». Для необученной записи BTFN дал бы «состоится», значит
запись **была обучена ранее**, за пределами окна захвата, и обучена в
противоположную сторону.

## Классификация всех десяти промахов по причине

| Причина | Сколько | Устранимо? |
|---|---|---|
| выход из цикла (`0xf00002b8`, `0xf00015e0`, `0xf00015fc`) | 3 | нет, кроме предсказания длины цикла |
| холодная запись, работал BTFN (`0xf0000314`, `0xf0000324`, `0xf0000840`) | 3 | нет, первое исполнение |
| обучение или переобучение (`0xf00015d0`, `0xf00015fc`, `0xf0001110`) | 3 | частично, ценой другой политики счётчика |
| запись обучена вне окна (`0xf0001120`) | 1 | не определить по этому захвату |

Ни одна из групп не указывает на дефект: **шесть промахов из десяти
принципиально неустранимы**, остальные — плата за инерцию счётчика. Это
согласуется с оценкой по симуляции: потолок дальнейшей работы над точностью
составляет около 1.2% времени исполнения.

## Как повторить замеры симуляции

`sim_data/ladder.sh` переключает три `define` в
`scr1/src/includes/scr1_arch_description.svh`, прогоняет
`TARGETS="dhrystone21 coremark"` на каждой из четырёх конфигураций и
восстанавливает заголовок через `trap ... EXIT`.

`sim_data/ladder_with_counters.sh` делает то же, но дополнительно собирает
счётчики. **Счётчики требуют временной правки RTL** — в `scr1_pipe_exu.sv`, под
`` `ifdef SCR1_TRGT_SIMULATION ``, добавляется блок с `bpc_branches`/`bpc_taken`/
`bpc_mispred`/`bpc_cycles` и `final`-блоком, печатающим строку `BPSTAT`. В дереве
ядра этот блок **не оставлен** (убран после замеров), поэтому для повторения его
нужно добавить заново; текст блока приведён в разделе «Счётчики переходов и
промахов». На синтез и на плату он не влияет — только симуляция.

## Оговорка про соответствие захвата и симуляции

Захват ILA и прогоны симуляции — **разные программы**: на плате исполнялся тест,
загруженный по XMODEM, в симуляции — dhrystone и coremark из дерева `sim/tests`.
Поэтому доля промахов 2.17% (окно ILA) и 6.75% (симуляция, суммарно по двум
тестам) друг другу не противоречат: это разный код и разные окна наблюдения.
Совпадает главное — порядок величины остаточных потерь и вывод о том, что
основные промахи приходятся на выходы из циклов и необученные записи.
