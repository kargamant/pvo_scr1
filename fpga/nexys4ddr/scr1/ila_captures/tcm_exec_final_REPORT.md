# Отчёт по захвату `tcm_exec_final.ila`

Разбор потактового ILA-захвата исполнения теста Dhrystone из TCM на живой плате
Nexys A7-100T (SCR1, cpuclk 30 МГц). Цель документа — чтобы по дампу можно было
понять: **в какой момент что делало ядро, где шло чтение/запись, где бежал код,
какие инструкции выполнялись и как это читать.**

Файлы: `tcm_exec_final.ila` (открыть в Vivado) и `tcm_exec_final.csv` (для скриптов).

---

## 1. Как был сделан захват

| Параметр | Значение |
|---|---|
| Триггер | `i_scr1/tcm_imem_req == 1` (первая выборка инструкции из TCM) |
| Прочие 33 щупа | `don't-care` (сброшены явно перед армом) |
| Режим триггера | `BASIC_ONLY`, `TRIGGER_CONDITION = AND` |
| Позиция триггера | 100 (100 сэмплов пред-истории до события) |
| Режим захвата | `ALWAYS` (каждый такт подряд) |
| Глубина | 4096 сэмплов ≈ 136 мкс @ 30 МГц |
| Действие оператора | `g` → `f0000200` в minicom (запуск теста) |

Захват ловит **момент старта исполнения из TCM** и 136 мкс после него.

> ⚠️ **Важно при чтении:** `tcm_imem_rdata` (слово инструкции) возвращается на **1 такт
> позже**, чем выставлен `tcm_imem_addr` (регистровое чтение памяти). Поэтому
> **поток адресов `tcm_imem_addr` — точный**, а связка «адрес ↔ конкретное слово»
> может быть смещена на один такт. Управляющий поток (куда идёт PC) читаем по адресам.

## 2. Карта сигналов (что смотреть)

| Сигнал | Смысл |
|---|---|
| `i_scr1/tcm_imem_req` / `_req_ack` | идёт ли выборка инструкции из TCM (рукопожатие) |
| `i_scr1/tcm_imem_addr` | **PC — адрес выбираемой инструкции** (главный сигнал) |
| `i_scr1/tcm_imem_rdata` | слово инструкции (с задержкой 1 такт) |
| `i_scr1/tcm_dmem_req` / `_req_ack` | идёт ли обращение к данным в TCM |
| `i_scr1/tcm_dmem_cmd` | 0 = чтение (load), 1 = запись (store) |
| `i_scr1/tcm_dmem_width` | 00 = byte, 01 = half, 10 = word |
| `i_scr1/tcm_dmem_addr` / `_wdata` | адрес и значение обращения к данным |
| `axi_imem_*`, `axi_dmem_*` | внешние шины — в этом окне **молчат** (весь трафик в TCM) |

Сводка окна: `tcm_imem_req`=1 в **3151** тактах (77 %), `tcm_dmem_req`=1 в **807**
тактах (20 %), 48 уникальных адресов кода в диапазоне **F0000200…F00002BC**,
807 записей в данные (0 чтений), все — слова, диапазон **F0000104…F00048D8**.

---

## 3. Временная шкала — что происходило и когда

Захват целиком попал на **startup / crt0** (инициализацию перед основным циклом
Dhrystone). Три фазы:

### Фаза A. Вход в код (сэмпл 100 — триггер)
```
smp 100  PC=F0000200   JAL      ← точка входа (g f0000200), прыжок в старт
smp 101  PC=F0000204   AUIPC    ┐ вычисление
smp 102  PC=F0000208   ADDI     ┘ базового адреса данных
```
Триггер точно на `F0000200` подтверждает: поймали именно старт по команде `g`.

### Фаза B. Развёрнутый пролог записи (сэмплы ~103…212)
Линейная цепочка **STORE**-инструкций, адреса кода растут по 4 (`F000020C → 210 →
214 → … → 2AC`), каждая встречается **ровно 1 раз** — это **развёрнутый цикл**
(`-funroll-loops`). Каждый store занимает **2 такта**:
```
smp 105  imem_req=0  dmem_req=1  dmem_addr=F0000104   ← store исполняется (данные)
smp 106  imem_req=1  imem_addr=F0000214               ← выборка следующей инстр.
```
Данные пишутся в TCM подряд словами: `F0000104, F0000108, F000010C, …`.
**Здесь и находится «где проходит запись» на раннем этапе.**

### Фаза C. Плотный цикл инициализации (сэмплы 213…до конца) — 777 итераций
После пролога — **цикл из 4 инструкций** по адресам `F00002B0…F00002BC`.
Одна итерация = **5 тактов**:
```
F00002B0  AUIPC   — вычислить указатель
F00002B4  STORE   — sw: записать слово в память
F00002B8  ADDI    — инкремент указателя
  (1 такт пузыря — исполнение store на dmem-порту)
F00002BC  BNE     — обратный переход на F00002B0, пока указатель ≠ конца
```
Ветвление `fec59ce3` = **`bne`** (branch-not-equal) с отрицательным смещением →
**цикл**. За окно выбирается **777 раз**, строго каждые **5 тактов**. Пишет
последовательные слова (`dmem_wdata`: `F0003CBC, F0003CC0, F0003CC4…`) — это
инициализация массива указателей в crt0.

## 4. Где что: чтение, запись, исполнение

| Что искать | Где в дампе |
|---|---|
| **Исполнение кода** | `tcm_imem_req=1`, `tcm_imem_addr` растёт по 4 (линейно) или прыгает (ветви) |
| **Запись в память** | `tcm_dmem_req=1` **и** `tcm_dmem_cmd=1` — здесь `dmem_addr`/`dmem_wdata` = что и куда |
| **Чтение из памяти** | `tcm_dmem_req=1` **и** `tcm_dmem_cmd=0` — в этом окне таких **нет** (0 load'ов) |
| **Ветвление (переход)** | `tcm_imem_addr` = `F00002BC` (наш `bne`) |
| **Стрктурный пузырь** | такт, где `imem_req=0`, но `dmem_req=1` (конвейер ждёт store) |

> Почему нет чтений данных и почти нет записей «полезных данных» теста: образ собран
> с `-O3 -flto`, оптимизатор держит переменные Dhrystone в **регистрах**. Всё, что
> видно в `tcm_dmem` — это записи инициализации на старте (crt0), а не сам меряемый цикл.

---

## 5. Поведение предсказателя переходов (главное)

Смотрим переход «ветвление → цель цикла» потактово:
```
smp 220  PC=F00002BC   (bne, обратный)
smp 221  PC=F00002B0   (цель цикла)   ← СЛЕДУЮЩИЙ ЖЕ ТАКТ, без пузыря
```
**Между выборкой обратного `bne` и выборкой его цели — 0 тактов пузыря.** Ядро на
каждой итерации сразу тянет `F00002B0`, а не «проваливается» на `F00002C0`
(fall-through). Вывод:

> Статический предсказатель **BTFN (Backward-Taken)** предсказывает обратный `bne`
> как **взятый — верно все 777 итераций подряд, со штрафом 0 тактов**.

Единственный пузырь в итерации (5-й такт) — **структурный, из-за store**
(`dmem_req=1`), а не из-за ветвления. Если бы предсказатель ошибался, было бы
+2–3 такта на итерацию (сброс конвейера + перевыборка) — их нет.

**Что это значит для оценки предсказателя:** на регулярных циклах BTFN даёт
идеальное предсказание при нулевой цене. Цену *ошибки* в этом окне не видно — она
проявится один раз на **последней** итерации (переход не взят), которая в окно не
попала. Чтобы её поймать — отдельный захват с триггером на выход из цикла
(см. раздел 7).

## 6. Как открыть и читать в Vivado

```tcl
display_hw_ila_data [read_hw_ila_data {…/ila_captures/tcm_exec_final.ila}]
```
1. Курсор на **сэмпл 100** (маркер `TRIGGER`) — это `PC=F0000200`, старт.
2. `tcm_imem_addr` (Radix → Hex): ровный рост по 4 = линейное исполнение; повтор
   `F00002B0…BC` = цикл.
3. `tcm_dmem_req` + `tcm_dmem_cmd`: всплески = записи инициализации; смотри
   `dmem_addr`/`dmem_wdata`.
4. Наведи на `F00002BC` → следующий сэмпл `F00002B0` без разрыва = верное
   предсказание перехода.

Если сигналы без имён (`probe0…`) — не подхватился `.ltx`:
```tcl
set_property PROBES.FILE {…/impl_1/nexys4ddr_scr1.ltx} [current_hw_device]
```

## 7. Что дальше (по желанию)

- **Цена мисспредикта:** захват с триггером `tcm_imem_addr == F00002C0` (fall-through
  цикла) или на большем окне — поймать единственную ошибку BTFN на выходе из цикла,
  увидеть пузырь сброса конвейера.
- **Настоящий цикл Dhrystone:** окно 4096 тактов (136 мкс) короче времени до
  меряемого цикла; чтобы попасть в него — глубже буфер или триггер по адресу
  функции `Proc_*` / основного цикла.
- **Реальный load/store-трафик:** пересобрать тест без `-O3` (переменные в памяти) —
  тогда `tcm_dmem` покажет полный поток обращений к данным.
