# Секции ELF и назначение файлов `.bin`, `.elf`, `.map`, `.dump`

Эта памятка объясняет таблицу секций, которую обычно выводит `objdump`, и роль основных артефактов bare-metal сборки.

## 1. Столбцы таблицы секций

```text
Idx Name        Size      VMA       LMA       File off  Algn  Flags
```

| Столбец | Значение |
|---|---|
| `Idx` | Номер секции в ELF |
| `Name` | Имя секции |
| `Size` | Размер секции в байтах, записанный в hex |
| `VMA` | Адрес секции во время исполнения |
| `LMA` | Адрес, откуда загружается её начальное содержимое |
| `File off` | Смещение содержимого секции от начала ELF-файла |
| `Algn` | Требуемое выравнивание, например `2**6 = 64` байта |
| `Flags` | Свойства секции |

### VMA и LMA

- `VMA` — адрес, по которому процессор обращается к секции во время исполнения.
- `LMA` — адрес, где начальные байты секции находятся при загрузке.

Например, у `.data` значение `LMA` может указывать во Flash, а `VMA` — в RAM. Тогда startup-код копирует `.data` из Flash в RAM. Если `VMA == LMA`, такое перемещение не требуется.

### Основные флаги

| Флаг | Значение |
|---|---|
| `CONTENTS` | Секция содержит реальные байты в ELF |
| `ALLOC` | Секции выделено адресное пространство во время исполнения |
| `LOAD` | Начальное содержимое требуется загрузить в память |
| `READONLY` | Секция не предназначена для записи |
| `CODE` | Машинные инструкции |
| `DATA` | Данные, а не инструкции; вместе с `READONLY` — константы |
| `THREAD_LOCAL` | Отдельный экземпляр данных для каждого потока |
| `DEBUGGING` | Отладочная информация, не загружаемая в память процессора |
| `OCTETS` | Размер измеряется в восьмибитных байтах |

`ALLOC` не означает, что секция занимает место в `.bin`. Например, `.bss` и `.stack` резервируют RAM, но не содержат загружаемых байтов.

## 2. Основные секции программы

### `.text.crt`

Код C Runtime, выполняющийся до `main()`:

- reset/startup-код;
- установка `sp` и `gp`;
- обнуление `.bss`;
- обработчики trap/interrupt;
- переход в `main()`.

В рассматриваемом образе размер секции равен `0x504 = 1284` байта, а entry point `0x200` находится внутри неё.

### `.text`

Основной исполняемый код программы: функции теста, библиотеки, UART, `printf` и прочие машинные инструкции.

Для примера:

```text
.text.crt + .text
= 0x504 + 0x3170
= 0x3674
= 13 940 байт
≈ 13,61 КиБ
```

Для оценки статического объёма инструкций суммируются секции с флагом `CODE`.

### `.rodata`

Данные только для чтения:

- строковые литералы;
- константные массивы;
- таблицы CRC;
- иногда jump tables для `switch`.

Это не инструкции. Обращения к `.rodata` обычно проходят через интерфейс данных и D-cache.

### `.data` и `.sdata`

Глобальные и статические переменные с заданным начальным значением:

```c
int counter = 10;
```

`.sdata` содержит небольшие переменные, к которым RISC-V может обращаться короткими инструкциями относительно регистра `gp`.

### `.bss` и `.sbss`

Неинициализированные либо изначально нулевые глобальные и статические переменные:

```c
static unsigned char buffer[2000];
int counter;
```

Нули не хранятся в ELF и `.bin`. Startup-код обнуляет выделенный диапазон памяти перед вызовом `main()`.

`.sbss` — вариант для небольших переменных, адресуемых относительно `gp`.

### `.tdata` и `.tbss`

Thread-local storage:

- `.tdata` — инициализированные thread-local переменные;
- `.tbss` — изначально нулевые thread-local переменные.

Каждый поток должен иметь отдельную копию этих данных. В однопоточной bare-metal программе секции часто пусты.

### `.stack`

Резерв адресного пространства для стека. В примере:

```text
VMA  = 0x07ffc000
Size = 0x4000 = 16 КиБ
конец области = 0x08000000
```

Стек обычно растёт от верхнего адреса в сторону меньших адресов. Секция не имеет `CONTENTS`, поэтому 16 КиБ нулей в `.bin` не записываются. Её размер — резерв, а не фактическое потребление программы.

### `.riscv.attributes`

Служебные метаданные о RISC-V ISA и ABI: используемые расширения, архитектурные атрибуты объектных файлов и другие параметры. В память процессора секция не загружается.

## 3. Отладочные секции

Секции `.debug_*` используются GDB и другими инструментами. Они увеличивают ELF-файл, но не занимают память целевой программы.

| Секция | Назначение |
|---|---|
| `.debug_info` | Функции, переменные, типы и области видимости |
| `.debug_abbrev` | Форматы записей для `.debug_info` |
| `.debug_loclists` | Расположение переменных в регистрах или на стеке для разных PC |
| `.debug_aranges` | Связь диапазонов адресов с единицами компиляции |
| `.debug_rnglists` | Диапазоны адресов функций и областей видимости |
| `.debug_line` | Соответствие машинных адресов строкам исходного кода |
| `.debug_str` | Имена функций, типов и переменных |
| `.debug_line_str` | Имена и пути исходных файлов |

## 4. Карта рассматриваемого образа

```text
0x00000000  .text.crt
0x00000504  .text
0x00003674  .rodata
0x00003e30  .sdata
0x00003e3c  .sbss
0x00003e50  .bss
0x00004620  конец основной области

0x07ffc000  .stack
0x08000000  вершина стека
```

Последняя секция с загружаемым содержимым заканчивается по адресу `0x3e3c`, поэтому размер сырого бинарника равен:

```text
0x3e3c = 15 932 байта
```

После запуска дополнительно используются области, которых нет в `.bin`:

```text
.sbss + .bss = 20 + 2000 = 2020 байт
stack        = 16 384 байта резерва
```

## 5. Роль файлов сборки

Типичная последовательность:

```text
.c/.S -> .o -> линковка -> .elf
                           |-- objcopy -> .bin
                           |-- objdump -> .dump
                           `-- linker  -> .map
```

### `.bin`

Сырой массив байтов, который передаётся загрузчику и записывается в DDR или TCM.

В `.bin` нет:

- адреса загрузки;
- entry point;
- имён функций;
- таблицы секций;
- символов и отладочной информации.

Поэтому загрузчику отдельно нужно сообщить адрес размещения и адрес запуска программы.

### `.elf`

Полный результат линковки. Обычно содержит:

- код и данные;
- VMA/LMA секций;
- entry point;
- загружаемые сегменты;
- таблицу символов;
- отладочную информацию;
- архитектуру и ABI.

ELF используется для GDB/OpenOCD, JTAG-загрузки, получения `.bin`, дизассемблирования и разбора аварий по адресу PC. ELF, соответствующий конкретному прошитому бинарнику, желательно сохранять.

### `.map`

Текстовый отчёт линкера. Показывает:

- какие объектные файлы и библиотеки вошли в программу;
- сколько памяти заняла каждая функция или библиотека;
- адреса символов;
- расположение секций по memory regions;
- padding и выравнивание;
- удалённые секции;
- размещение code, data, stack и heap.

`.map` особенно полезен для поиска причины роста программы и проверки linker script. На плату он не загружается.

### `.dump`

Текстовый результат `objdump`, например:

```bash
objdump -x -d -S program.elf
```

Может содержать заголовки ELF, таблицу секций, символы, дизассемблирование и строки исходного кода. Используется, чтобы:

- проверить сгенерированные инструкции;
- увидеть применение расширения RISC-V `C`;
- исследовать циклы и обращения к памяти;
- сопоставить exception PC или адрес ILA с инструкцией;
- оценить размеры секций.

`.dump` не участвует в исполнении и может быть повторно получен из `.elf`.

## 6. Краткое сравнение

| Файл | Главная роль |
|---|---|
| `.bin` | Загрузить программу в память платы |
| `.elf` | Сохранить полное машинное представление программы и данные для отладки |
| `.map` | Понять решения линкера и вклад отдельных компонентов |
| `.dump` | Читать секции, символы и дизассемблированный код |

Для воспроизводимых экспериментов полезно сохранять все четыре файла для каждого набора параметров кэша и соответствующего bitstream.
